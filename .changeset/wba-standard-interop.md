Experimental AdCP 3.3 identity: align Web Bot Auth verification with what Cloudflare's `web-bot-auth` accepts. These changes affect the experimental `@adcp/sdk/identity-3.3` surface and the `verifySignature` and `verifySignatureAsync` helpers that `@adcp/sdk/signing/server` exports. The AdCP RFC 9421 profile is unchanged.

- **Other signatures are not read.** `verifyWebBotAuth` selects the one `Signature-Input` member tagged `web-bot-auth` and ignores members with other tags, which WBA section 5.2.2 allows. A second `web-bot-auth` member or a second `Signature-Agent` member is still a 403.
- **The `Signature-Agent` origin is https only.** The verifier refused an `http://` member value only because the directory fetch then failed. It now refuses any value that is not exactly the canonical https origin string (lowercase host, no default port, and no path, trailing `/`, query, fragment, or userinfo) with 403 before any fetch. `SignatureDirectoryResolver` applies the same rule to the origin it is given.
- **`type=directory` as a Token.** WBA draft -00 makes the `Signature-Agent` `type` parameter a Token, and the verifier refused the Token `directory`, accepting only the String `"directory"`. It now reads either form, as Cloudflare's reference does. Any other type is still ignored, which leaves no member to resolve (403).
- **Unusable directory keys are ignored.** `verifyKeyDirectory` and `SignatureDirectoryResolver` skip a key the profile cannot use, such as a P-256 key, together with any signature it made (RFC 7517 section 5). Every usable key must still sign the directory. A directory with no usable key, or one that publishes a private JWK member (`d`, `p`, `q`, `dp`, `dq`, `qi`, `oth`, or `k`) for any key, usable or not, is a discovery failure. A directory that listed a P-256 key used to be refused with `directory_unsupported_key`.
- **Ed25519 only.** Web Bot Auth signs and verifies with Ed25519 keys only, as Cloudflare's edge and Rust crate do. RSA-PSS-SHA512 is removed from request signing and verification, from key-directory publishing and verification, and from origin revocation lists, which are signed and verified as `EdDSA` only. `signWebBotAuth`, `createSignedSignatureDirectory`, `createWebBotAuthFetch`, `createSignedOriginRevocationList`, and the server and webhook wire-up refuse an RSA key. A request with `alg="rsa-pss-sha512"` is a 403, and a verifier ignores an RSA key in a directory. `verifySignature` and `verifySignatureAsync` from `@adcp/sdk/signing/server` no longer verify `rsa-pss-sha512`; only Web Bot Auth used it, and the AdCP RFC 9421 profile allows only `ed25519` and `ecdsa-p256-sha256`. ES256 stays on the AdCP RFC 9421 profile, which is unchanged.
