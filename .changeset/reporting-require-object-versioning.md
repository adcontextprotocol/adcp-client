S3 and Azure row providers now require versioning. Their native version is the write-unique S3 `VersionId` or Azure blob `versionId` only; the ETag fallback is removed because ETags are content-derived, so a delayed exact-version delete (such as an intent sweep removing an abandoned upload) could remove a replacement object re-created with identical bytes at the same key. The S3 probe fails closed with `UNSAFE_BINDING` unless `GetBucketVersioning` reports `Enabled` (it now also needs `s3:GetBucketVersioning`), the Azure probe requires its create-only write to return a `versionId`, and `putIfAbsent` (create and adopt paths) refuses results without a version. Reads and deletes pin the version ID only. `runReportingRowObjectProviderConformanceV1` gains a `write-unique-version` check (re-creating identical bytes after a delete must yield a new native version, and deleting the stale version must leave the new object), and the filesystem provider's version now includes nanosecond birth and modify times with a random sub-millisecond mtime so it is write-unique too. These providers are not yet published, so this is not breaking for any released user.
