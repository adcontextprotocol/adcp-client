Add a transactional PostgreSQL reporting lifecycle activity bridge with schema-conformant health notifications, finality-aware account activity, stable event identity, fenced crash recovery, tenant-scoped pagination, and reuse of persistent notification webhook delivery. Finality-only lifecycle transitions are newly recorded for internal activity but do not emit the health-only AdCP webhook. Pre-v14 transitions without a recorded finality resolve their baseline through `ReportingLedgerStore.resolveTransitionFinalityBaseline`, which persists `none` rather than reconstructing one. The lifecycle decision and the store's compare-and-set therefore read one committed baseline. No stored timestamp can prove which revisions had committed when a pre-v14 row was recorded — payload timestamps rank creation rather than commits, and insert wall clocks tie and step backward — and guessing suppresses a real snapshot-to-official change permanently, so upgrades record at most one redundant finality-only internal activity entry instead. The recovery worker now commits each transition's recipient set onto its claimed activity row before any external send and replays that committed set through the new `NotificationEvent.freezeRecipients` barrier, so a crash between send and settlement followed by a subscription replacement can no longer deliver the same notification again under a new destination generation and idempotency key. `REPORTING_LEDGER_FINALITY_WRITER_FENCE_MIGRATION` adds a `NOT VALID` check constraint that permits historical rows but rejects any new transition lacking a recorded finality, making the one-redundant-event-per-obligation upgrade bound enforceable against a pre-v14 writer that survives a rolling deploy. Operational delivery-authority failures (`authorization_error`, `credential_unavailable`, `subscription_stale`) are now classified by the exported `notificationSuppressionDisposition` and release the recovery claim instead of settling the activity as delivered, so a transient store, authorization or credential failure no longer silently drops a notification. A second barrier, `NotificationEvent.beforeExternalAttempt`, records the moment an external POST begins, which makes the frozen recipient set revisable until then — closing the window where a destination replacement lands between candidate enumeration and the first POST — and immutable afterwards. Recipient intent is stored relationally in `<activity_table>_recipients` keyed by intent round, so a maximum fanout of maximum-length references is storable without a serialized-document size cap that could poison a claim; `maxRecipients` defaults to the notification runtime's 10,000 ceiling and unstorable configurations are rejected at construction.
