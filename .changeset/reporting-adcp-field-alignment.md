**Breaking: reporting row storage field alignment.** Row storage now stores every value in the format AdCP already defines for it, and `{period_date}` is the period's calendar date in its `source_timezone`, not UTC. This ships before any adopter activated row storage in production, so the rename is deliberate and one-time. See `docs/migration-reporting-row-storage-alignment.md`.

- **Names and bounds.** In `adcp_reporting_row_chunks`, `object_key` is now `object_ref` and `native_version` is `native_version_ref` (both 1 to 1024 characters, enforced by new `CHECK` constraints), `physical_byte_count` is `size_bytes` (the stored object's size, as in the AdCP file manifest), and `byte_count` is `canonical_size_bytes` (uncompressed canonical bytes). `adcp_reporting_row_sets.canonical_byte_count` is `content_size_bytes` (the size of the content its `content_sha256` covers, which for a revision includes the envelope), and `encoding = 'adcp_canonical_jsonl_v1'` is replaced by AdCP's `format = 'jsonl'` and `algorithm = 'adcp_jcs_rows_v1'`. TypeScript follows: `ReportingRowChunkLocatorV1` (`objectRef`, `nativeVersionRef`, `sizeBytes`), the `ReportingRowObjectProviderV1` inputs (`objectRef`, `nativeVersionRef`; `putIfAbsent` returns `nativeVersionRef`), `ReportingRowBindingSelectionInputV1.content_size_bytes`, `ReportingRowSetHandleV1.contentSizeBytes`, and `REPORTING_ROW_ENCODING_V1` replaced by `REPORTING_ROW_FORMAT_V1` and `REPORTING_ROW_ALGORITHM_V1`. The format and algorithm tokens feed no digest: no chunk, segment, manifest or `revision_content_sha256` value changed, and the golden fixture only swapped its top-level label.
- **`{period_date}`.** The placeholder keeps its name and now renders AdCP's `YYYY-MM-DD` for the period start in the period's `source_timezone`, as one path segment (it was the UTC date split into `yyyy/MM/dd` directories). A missing, unknown or non-IANA timezone fails the write with `INVALID_INPUT` instead of guessing. `ReportingRowSetPrepareInputV1` takes `sourceTimezone` beside `periodStart`. The key template string is unchanged, so binding identities stay valid. Rendered keys are now refused above AdCP's 1024-character `object_ref` bound.
- **No re-download inside the commit transaction.** `ReportingRowStorageV1.assertObjectsPresent` used to read each adopted object in full (a 17 MiB chunk) while holding the account and object locks. `ReportingRowObjectProviderV1` gains an optional `stat({ objectRef, nativeVersionRef })` returning `{ nativeVersionRef, sizeBytes }` or `null`; native versions are write-unique, so the same echoed version at the recorded size proves the object unchanged. The filesystem, GCS, S3 and Azure providers implement it, and the provider conformance suite checks it (`version-pinned-stat`). A custom provider without `stat` keeps the full read. Lock semantics are unchanged.
- **Upgrading.** Re-apply `REPORTING_ROW_STORAGE_MIGRATION` in a maintenance window before starting new binaries, and do not run an older writer afterwards; a new binary refuses to start row storage against an un-migrated database. It is idempotent, serialized by an advisory lock, works on a fresh install, renames columns in place where the old names exist, adds the length checks, and rewrites open write intents' `created_objects` to the new keys. Object keys already rendered under the UTC rule are not rewritten; reads and deletes use the recorded `object_ref`. If you installed the row-storage tables but never activated them, the in-place migration is enough (the migration guide explains the optional drop and re-sync). Custom object providers must rename `key` to `objectRef` and `nativeVersion` to `nativeVersionRef`, and should add `stat`. Other SDKs that share `test/fixtures/reporting-row-storage-v1.json` must adopt the same labels and storage names and reproduce the same bytes.

New `reportingPeriodDate(periodStart, sourceTimezone)` (in `reporting/ledger/schedule`) computes the source-timezone calendar date with `Intl.DateTimeFormat` and fails closed on an invalid instant or timezone.
