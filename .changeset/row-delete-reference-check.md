Reliable Reporting: every external row-object delete now skips an object another row set still references. A custom object `keyTemplate` that omits `{account_key}` and `{revision_key}` lets two obligations or accounts with identical chunk content share one object (a create-only write adopts the existing bytes), and period retirement, row pruning and the intent sweep could delete it while the other row set was still live, failing its reads with `ROWS_INTEGRITY_FAILED`. Retirement, compaction and the intent sweep now delete an object only when no live row set outside the operation references the same binding, key and native version and no other open write intent created it; the check and the delete run under a per-object advisory lock that a commit adopting an existing object also takes (and holds until its chunk rows commit, after re-reading the object), so a concurrent adoption can no longer lose its object. A commit whose adopted object was deleted first now fails with `STATE_UNAVAILABLE` instead of recording a dangling reference. A skipped object is deleted when the last row set that references it is retired. `assertCompactionSafeKeyTemplates` is kept as defense in depth. No schema change.
