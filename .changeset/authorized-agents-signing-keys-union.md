New `resolvePublisherSigningKeyPin(scope)` combines `signing_keys` when more than one `authorized_agents[]` entry matches one agent under AdCP 3.3 (the SDK side of adcontextprotocol/adcp#9016). An example is an origin-only entry next to the agent's full URL. The agent is pinned for that publisher only if every matching entry carries `signing_keys`. One matching entry with none, absent or empty, means no pin. When every matching entry pins, the result is the union of their keys in document order. A key repeated identically appears once, and a copy carrying a `revoked_at` is kept. Pass a `ResolvedAgentScope` from `resolveAgentProperties`, which uses `matched_entries` at 3.3 or later and `matched_entry` below 3.3, or pass the matching entries themselves. The result is `undefined` for no pin and is never `[]`, so it drops into `PublisherSigningKeyPin.signingKeys`, and `?? null` gives a `refresh` result. With one matching entry, as below 3.3, it is that entry's own pin. Exported from `@adcp/sdk` and `@adcp/sdk/discovery`.

The SDK makes no pin decision from `adagents.json` itself: webhook `publisherPins` are supplied by the caller, and supply-path verification only lists `signing_keys` as an understood field. So this release adds the helper and documentation, and no existing behaviour changes. `AuthorizedAgent` gains an optional `signing_keys` field. The `matched_entries` and `AgentDirectoryPublisher.signing_keys_pinned` docs now state the rule, which the AAO directory follows too. This supersedes the 17.0.0-beta note that the AAO registry reports keys as pinned when any matching entry pins one.
