Security: `list_accounts` `account_requests[]` and `request_account` responses no longer echo write-only account credentials. A resolved AdCP 3.3 account request embeds a full `Account`, and the SDK served it without the scrub it applies to `list_accounts` account rows. If your seller stored any of these on the account (or spread the inbound request into `requested`), they reached the buyer and the idempotency replay cache: `billing_entity.bank`, `governance_agents[].authentication` (the bearer the seller uses to call the governance agent), `notification_configs[].authentication.credentials` (webhook signing secrets), and `destination_billing_entity`. Affected: `request_account` on `createAdcpServer` and `createAdcpServerFromPlatform` since 17.0.0-beta.10, raw `listAccounts` handlers returning `account_requests` since 17.0.0-beta.10, and `accounts.listRequests` on the platform path since 17.0.0-beta.12. Stable 16.x lines do not serve account requests and are not affected.

Both paths now run each request's `account` through the same scrubber as account rows, and strip the same credential fields from `requested`, on the completed and failed arms and before the response is cached for replay. Your stored records are not modified. The account scrubber now also drops `governance_agents[].authentication` on every account it handles, which closes the same gap for raw (`createAdcpServer`) `list_accounts`, `sync_accounts` and `get_media_buys` handlers that returned it. No code change is needed. If a credential may have been served, rotate it: webhook signing secrets and governance-agent tokens first.
