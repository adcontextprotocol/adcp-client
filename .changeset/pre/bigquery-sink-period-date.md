The BigQuery warehouse sink now computes `period_date` with the shared `reportingPeriodDate` helper, the same one that renders `{period_date}` in object-storage keys, and fails closed. Before, a missing timezone defaulted to UTC, an unusable timezone fell back to the UTC date, and an unusable start became `NULL`, so a malformed period was loaded under a guessed or empty date and partitioned into the wrong day. Valid IANA zones already produced the source-local date and are unchanged. Now the sink throws `Cannot compute period_date for revision <id>` before reading any rows. The batch stays retained and every run fails until that revision's period is repaired (or the runtime's timezone data is upgraded); `reset({ discardRetainedPlan: true })` restarts from the beginning, so empty the destination tables first. A timezone given as a UTC offset (for example `+05:30`), which is not an IANA zone, is now rejected rather than accepted on runtimes that allow it. `period_date` remains the start's date only, not a coverage range. `scripts/validate-reporting-gcp.mjs` gains a check that loads America/Los_Angeles, Asia/Tokyo and UTC obligations and asserts each `period_date`.
