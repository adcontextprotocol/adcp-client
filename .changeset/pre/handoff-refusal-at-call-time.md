`ctx.handoffToTask(...)` now refuses a handoff the framework cannot dispatch when it is called, not after the handler returns (#3761). For a request that carries `push_notification_config`, an external handoff (`{ settlement: 'external' }`), or a framework handoff on a server without task webhooks, throws the same structured `AdcpError` (`UNSUPPORTED_FEATURE`, `recovery: 'correctable'`, `field: 'push_notification_config'`, `details: { feature: 'task_webhook_delivery' }`) from the `handoffToTask` call, so handler code after it, such as a call to a remote agent, does not run. The tool's other request-determined handoff refusals move to the call too, checked first in dispatch order: a wholesale `get_products` / `get_signals` request, an external handoff on a proposal-backed `create_media_buy`, and a request with no resolved account. External settlement on a process-local registry also fails at the call. Because the check runs at the call, a handler that builds a marker eagerly and then answers synchronously (`const h = ctx.handoffToTask(fn); if (fast) return sync; return h;`) now fails with `UNSUPPORTED_FEATURE` when the request carries `push_notification_config` and the server has no task webhooks. Call `handoffToTask` only on the path that returns it. New `ctx.canHandoffToTask(options)` returns `{ ok: true }` or `{ ok: false, error }` with that error, so a proxying handler can check before it starts remote work. On a tool that does not accept a handoff, it returns `ok: false`. Dispatch still runs the same check as a backstop. `RequestContext` gains the required `canHandoffToTask` member, so a hand-built `RequestContext` test double needs it too.
