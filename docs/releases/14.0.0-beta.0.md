# @adcp/sdk 14 prerelease notes

These cumulative notes cover the SDK 14 beta and release-candidate lines, beginning with
`14.0.0-beta.0` and including the compatibility and lifecycle hardening in
later beta releases. SDK 14 is the preview line for AdCP `3.2.0-beta.0`. It
adds the compact media-buy lifecycle, governance-plan adjustment reporting,
agent notification configuration, and the AdCP 3.2 request-signing profile
while retaining wire compatibility with supported AdCP 3.0 and 3.1 sellers.

Install the newest v14 prerelease explicitly:

```bash
npm install '@adcp/sdk@^14.0.0-0'
```

The npm `latest` tag remains on SDK 13. SDK 13 is the maintained stable line for AdCP 3.1; installing `@adcp/sdk` without a tag does not opt an application into this beta.

## Compatibility contract

| SDK line | Protocol surface | Supported seller wire versions | npm tag |
|---|---|---|---|
| 13.x | AdCP 3.1 stable | AdCP 3.0 and 3.1 through the bundled compatibility layer | `latest` |
| 14.0.0 beta | AdCP `3.2.0-beta.0` | AdCP 3.0, 3.1, and exactly `3.2.0-beta.0` | `beta` |

The beta pins an exact protocol artifact rather than a moving `3.2` alias. The bundled compatibility list contains released 3.0 and 3.1 versions, and the SDK continues to adapt legacy creative and media-buy wire shapes beneath the canonical public API. A seller must advertise its actual AdCP version; the SDK does not guess a newer signing or schema profile.

AdCP 3.2 is itself a beta. Later protocol betas can change schemas and will require a corresponding SDK beta rather than silently changing this package's behavior.

## Compact media-buy lifecycle

The generated client, server handler maps, request validators, response types, Zod schemas, task manifest, and per-tool declaration slices now include the seven compact lifecycle tools:

- `list_products` reads canonical published product offers synchronously.
- `request_proposals` creates actionable seller proposals.
- `refine_proposals` revises proposals with typed constraints and immutable lineage.
- `decline_proposals` terminally declines proposals.
- `buy_products` buys explicit published offers without a proposal round trip.
- `accept_proposal` accepts a committed new-buy, amendment, or cancellation proposal.
- `control_media_buy` applies operational controls that remain inside accepted commercial terms.

`AgentClient` exposes matching camel-case methods. Mutating methods accept the SDK's idempotency-aware request input, and the existing generic `executeTask()` path remains available.

`createAdcpServerFromPlatform()` now exposes the same lifecycle through the
first-class `mediaBuyLifecycle` platform interface. Compose it with `sales`
when one deployment must also serve the established 3.0/3.1 tool names.

MCP discovery defaults to the spec's active 3.2 `media-buy` profile whenever a
3.2 server registers a compact lifecycle handler. It omits deprecated
`get_products`, `create_media_buy`, and `update_media_buy` from `tools/list`,
but keeps configured compatibility handlers directly callable by older buyers.
Each listed tool and the list response expose the server's protocol pin under
`_meta.adcp_version`; the response also exposes `_meta.adcp_profile`.
Active-profile entries include their exact, self-contained draft-2020-12
request schemas. Compact-only sellers can implement current readback methods on
`mediaBuyLifecycle` without also defining deprecated handlers.

The established 3.x tools remain available for 3.0/3.1 interoperability. A
compact call is not silently field-cast into a legacy call because proposal
terms, feed versions, and revisions require orchestration. Capability discovery
should decide which lifecycle to use. See the complete [3.2 media-buy surface
and compatibility matrix](../guides/MEDIA-BUY-3.2-COMPATIBILITY.md).

AdCP 3.2 adds optional-key replay semantics to the already state-changing,
legacy-compatible `get_products` proposal-finalize variant. SDK 14 clients
automatically attach a key to proposal refinements with `action: 'finalize'`.
SDK 14 servers replay the variant when a valid key is supplied: synchronous
exact same-key retries return the cached committed proposal with
`replayed: true`, while HITL retries return the same submitted task envelope
for polling. Changed payloads conflict. The published
compatibility schema keeps the key optional, so an older caller that omits it
still executes but cannot receive cache-backed replay protection. Ordinary
catalog, brief, and non-finalizing refinement requests remain read-only.

SDK 14 treats `IDEMPOTENCY_CONFLICT` as a reconciliation stop, not an automatic
fresh-key retry. Look up the prior operation by natural key before deciding
whether a genuinely new intent should receive a new key.

Seller replay identity now includes the tool and trusted resolved
session/account identity, closing cross-tool and cross-tenant replay paths.
An SDK 13 cache entry encountered after upgrade returns
`IDEMPOTENCY_CONFLICT` rather than re-executing; see the 13-to-14 guide.

## Other 3.2 features

- `report_plan_adjustment` records seller-authenticated, append-only governance commitment adjustments with idempotent semantics.
- `sync_agent_notification_configs` declaratively registers, replaces, pauses, or clears agent-level notification subscriptions such as `capabilities.changed`.
- The generated measurement skill joins the packaged agent skills, and all bundled skills were refreshed from the signed 3.2 artifact.
- Generated documentation, error-code guidance, specialism manifests, and narrow `@adcp/sdk/types/<tool>` slices were refreshed from the exact signed beta artifact.

## Request signing

AdCP 3.2 changes the request-signing representation:

- signature and digest binary values use padded standard Base64;
- `Content-Digest` is mandatory for signed requests;
- AdCP 3.0 and 3.1 retain the legacy unpadded Base64URL profile;
- webhook signing remains on its existing legacy profile.

Servers that need a rolling upgrade may configure the internal
`signedRequests.covers_content_digest: 'either'` verifier policy so SDK 12/13
callers remain accepted. Their 3.2 capability response must still advertise
`covers_content_digest: 'required'`; SDK 14 projects that strict public contract
automatically. Move the internal verifier to `required` once every caller has
moved to the 3.2 profile.

The SDK selects the profile from trusted agent-version context and carries that version through A2A, MCP, signing fetches, and server verification. It does not infer a profile from attacker-controlled request fields. Applications that call the low-level signing API can use `requestSigningEncodingForVersion()` and should pass the negotiated `adcpVersion` wherever the signing/verifier options accept it.

If a low-level verifier has no trusted version pin, it accepts both binary
serializations while preserving the supplied digest capability. This keeps
frozen 3.0/3.1 verifier integrations working during upgrade without weakening
an explicitly required 3.2 digest policy.

## Media-buy lifecycle state

Server handlers should return business lifecycle state as `media_buy_status`. The framework owns the top-level task-envelope `status`. Compatibility overlays continue to accept the older handler shape where required, but new 3.2 implementations should not overload `status` with media-buy state.

## Type generation and build footprint

The 3.2 schemas use more `$defs`, intersections, conditionals, and shared canonical format types than 3.1. The generators now preserve those structures in TypeScript and Zod output, including non-empty tuples and primitive/open-string intersections. Repository build and type-check commands explicitly provide TypeScript an 8 GB heap.

Adopters normally should not need that heap. Prefer focused runtime entry points and narrow per-tool types such as:

```ts
import type {
  RequestProposalsRequest,
  RequestProposalsResponse,
} from '@adcp/sdk/types/request-proposals';
```

Import runtime schemas only from `@adcp/sdk/schemas`. Applications intentionally compiling the complete generated protocol barrel with `skipLibCheck: false` may still need a larger Node heap.

- Existing SDK 13 adopters: [Migrating from 13.x to the 14 prerelease](../migration-13-to-14.md)

Because this is a beta, test both sides of a mixed-version deployment: an SDK 14 buyer against the actual 3.0/3.1 sellers you still operate, and 3.0/3.1 buyers against any server upgraded to SDK 14. Keep SDK 13 available as the stable rollback line.
